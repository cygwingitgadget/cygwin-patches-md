Hi,

The attached patch fixes a startup race in user_info::initialize that makes new processes die with

  add_item ("\??\C:\Program Files\Git", "/", ...) failed, errno 1

after a 15 second hang. It is reported against Git for Windows at https://github.com/git-for-windows/git/issues/6368, where it can last until every MSYS process is gone because tools keep starting shells while the per-user section is stuck.

The current spinlock times out after 15 seconds and lets the waiter re-run mount_info::init on a table that may already hold "/". The patch replaces it with a named mutex next to the section: a live initializer is waited for, and one that died shows up as WAIT_ABANDONED, so the half-built section is cleared and rebuilt. Initialized sections still take the lock-free fast path. The one behavior change is that a process suspended indefinitely while initializing now makes later processes wait instead of dying after 15 seconds.

msys2/msys2-runtime#333 proposes making create_root_entry tolerate a second initialization (MOUNT_OVERRIDE) instead. That stops the crash, but a slow initializer that is still running can then be writing the table at the same time as the waiter.

Testing, on the Git for Windows runtime 3.6.10 with the identical change (it applies cleanly to main):

- Git for Windows CI: build, UI tests, MSYS2 test suites on all
  toolchains, and all Git test-suite shards passed.
- Stress test in Windows Sandbox: start sh.exe A, suspend it 3-15 ms
```
  into startup, start sh.exe B, then resume or kill A. 50 runs each:

			stock		 	patched
    A resumed		15 add_item crashes	0 (B waited in 20 runs)
    A killed		18 add_item crashes	0 (B waited in 16 runs)
    100 serial runs	0 failures		0 failures

  In the killed case B proceeded as soon as A died, through the
  abandoned-mutex path.
```

- Running on my workstation since; no startup time difference
  (about 150 ms per process either way, dominated by endpoint security).

I haven't built it against main itself, only the Git for Windows tree.
